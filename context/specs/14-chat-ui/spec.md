# Chat UI — Spec

**Status:** Draft
**Scope:** The Flow 4 frontend in `apps/web` — the product's main screen, mounted inside the protected app-shell from `[[../06-web-shell-and-auth-ui/spec|06]]`. A **sessions list** (`chat_sessions`, org-scoped, ordered by `updated_at` desc) with create / select / rename; a **conversation view** that renders `messages` and **streams** the assistant's answer as it arrives from `[[../13-chat-orchestrator/spec|13]]`; the **chat input field** (the single glass surface on this screen); a **model switcher** sourced from `ai_connections.default_model`; and explicit **loading / empty / error** states covering the orchestrator's unhappy paths. Answers, numbers, and tables render on **solid** surfaces (`ChatBubble` / `Card` / `MetricCard`) with `tabular-nums` for figures — never on glass.

## Context

This is the screen the whole product exists to deliver: the owner types *"quanto vendi em maio?"* and gets an exact figure computed against their live database. Everything before it — auth (`[[../05-login-jwt-sessions/spec|05]]`), the client DB connection (`[[../09-introspection-and-exposure/spec|09]]`), the AI key (`[[../11-ai-connection-claude/spec|11]]`) — is setup so that this conversation can happen. The shell (`[[../06-web-shell-and-auth-ui/spec|06]]`) already provides the glass sidebar + glass topbar, the design-system port (`AppBackground`, `GlassPanel`, `Card`, `MetricCard`, `TextField`, `ChatBubble`, `NavItem`, `Avatar`, `Button`, `useTheme`), the `QueryClient` + cookie-sending fetch wrapper, and the protected-route guard. This spec fills the protected home's placeholder with the real chat.

The backend half — the orchestrator that selects a parameterized query function, executes the SQL, calls Claude through the Vercel AI SDK, streams tokens, persists `messages`, and logs `function_call_logs` — is `[[../13-chat-orchestrator/spec|13]]` and is **called**, not implemented, here. This spec is the consumer of `13`'s endpoints and its streaming contract. The session/message list shapes and the send/stream request/response DTOs live as shared Zod contracts in `packages/shared`; the client validates against those, never a duplicated shape.

Two invariants from `[[../../constitution|Constitution]]` govern every line. **Multi-tenant isolation (anti-IDOR):** `org_id` is derived server-side from the JWT cookie; the client never holds, constructs, or sends a tenant id. Sessions and messages come back **already org-scoped** — the frontend asks for "my sessions," not "org X's sessions," and selecting a session sends only its `session_id` (which the backend re-scopes to the caller's `org_id`). **Glass only on chrome** (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`): the chat input field, the sessions sidebar, and menus may use glass; the answer bubbles, the numbers, the tables, the metric cards — the data the user reads — sit on solid, high-contrast surfaces. Never a number on glass; the product's precision value depends on legibility. All React work follows `react-best-practices` + `vercel-react-best-practices` (`[[../../rules/use-best-practices-skills|use-best-practices-skills]]`).

## Problem Statement

The protected shell renders a placeholder home; there is no way to actually ask a question. We need: (1) a **sessions list** populated from `chat_sessions` (org-scoped, `updated_at` desc) that lets the user create a new conversation, select one, and rename it — with the active session reflected in the URL so a conversation is deep-linkable and reload-safe; (2) a **conversation view** that loads a selected session's `messages` (user + assistant, in `created_at` order) on solid `ChatBubble`/`Card` surfaces, with figures in `tabular-nums`; (3) a **streaming display** that, on send, optimistically shows the user's message, then renders the assistant's answer **incrementally** as tokens arrive from `[[../13-chat-orchestrator/spec|13]]`, settling into the persisted message when the stream completes; (4) a **chat input** (the one glass surface) that sends the question, disables/locks while a stream is in flight, and supports Enter-to-send; (5) a **model switcher** defaulting to `ai_connections.default_model`, letting the user pick a model per the schema's "trocável no chat" note (the chosen model is recorded on the assistant `messages.model`); and (6) honest **loading / empty / error** states for the unhappy paths the orchestrator surfaces — **out-of-scope question**, **empty result**, **client DB down**, **AI key invalid/failed** — each rendered as a clear, non-alarming message on a solid surface rather than a raw error or a stuck spinner.

## Non-Goals

- **The orchestration backend.** Function selection, SQL execution, Claude calls, streaming production, message persistence, and `function_call_logs` are `[[../13-chat-orchestrator/spec|13]]`. This spec only sends questions and renders the stream/result it gets back.
- **The audit / observability view.** Surfacing `function_call_logs` (what the assistant queried, latency, success/failure) to the user is `[[../15-observability-sentry/spec|15]]`. The chat shows answers, not the call log.
- **Connecting the DB or the AI.** The consent/onboarding/exposure screens (`[[../10-connect-db-ui/spec|10]]`) and the Claude-key screen (`[[../11-ai-connection-claude/spec|11]]`) are owned elsewhere. This spec assumes a connected, `active` DB and AI connection exist and only **links out** to those screens when they are missing/`failed` (see the gating state below).
- **The shell itself.** Sidebar/topbar chrome, theme, routing scaffold, the guard, and the fetch wrapper are `[[../06-web-shell-and-auth-ui/spec|06]]`; here we consume them.
- **Deleting sessions, multi-user sessions, message editing/regeneration, export, search across conversations.** Not in v1 scope; create / select / rename only.
- **Charts/visualizations.** A tabular answer renders in a solid `Card` table; rich charting is deferred.
- **i18n framework.** Copy is inline pt-BR, matching `06`.

## Constraints

- **Mount point & layout.** The chat is a protected route under `06`'s app-shell `<Outlet />`. Within the shell's content area, a two-pane layout: a **sessions sidebar** (may be glass — it is chrome) and the **conversation column**. The conversation column is itself two solid regions — a scrollable **message list** (solid) and, pinned at the bottom, the **chat input** (the one glass surface). `<AppBackground />` is already rendered once by the shell; do not render a second one.
- **Routing.** The active session lives in the URL (e.g. `/chat/:sessionId`); `/chat` with no id shows the empty/new-conversation state. Selecting a session navigates (deep-linkable, reload-safe, back/forward works). The client sends only `session_id` in the path/body — **never** an `org_id`; the backend re-scopes by the cookie's `org_id` (anti-IDOR, `[[../../constitution|Constitution]]`). A `session_id` that isn't the caller's returns `404`/`403` from `13`; render a clean "conversa não encontrada" state, not a crash.
- **Data via TanStack Query.** Sessions list and per-session messages are **TanStack Query** queries against `13`'s endpoints through `06`'s shared fetch wrapper (`credentials: 'include'`). The sessions list is keyed and sorted client-side by `updated_at` desc (server returns it scoped + ordered; the client does not re-sort into a different order). Rename and "new session" are **mutations** that invalidate/patch the sessions cache; a successful send bumps the active session's `updated_at`, so the list re-orders to put it on top. No `useEffect`+`fetch` for any of this (`react-best-practices`).
- **Streaming the answer.** The live answer is **not** a TanStack Query — it is a streaming client (the Vercel AI SDK's React streaming hook/`useChat`-style consumer, or a thin `fetch` + `ReadableStream`/SSE reader matching `13`'s transport). On send: (a) optimistically append the user message to the visible list; (b) open the stream to `13`; (c) append an assistant bubble that fills **incrementally** as chunks arrive; (d) on `done`, reconcile the streamed text with the persisted assistant `messages` row and **invalidate the messages query** so the canonical server state wins; (e) on stream error, replace the partial bubble with the appropriate error state (below) — never leave a half-streamed bubble. The input is **locked** (disabled send, visible "respondendo…" affordance) while a stream is in flight; only one in-flight stream per session.
- **Glass only on chrome (enforced).** Glass (`GlassPanel`/`.glass`) is allowed **only** on the sessions sidebar, the chat input field, and any menus/popovers (the model switcher dropdown, the session "…" menu). The message list, every `ChatBubble`, any answer `Card`, any rendered table, and every `MetricCard` sit on **solid** surfaces. **No number, table, or reading-length answer text is ever placed on glass** (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`, `[[../../constitution|Constitution]]`). Figures use `tabular-nums` (the design system's `.ds-num`) so columns and currency align — precision must read as precise. Reading text is Inter on solid; `Space Grotesk` only for brand/section titles.
- **Model switcher.** A control in the conversation chrome (topbar of the conversation column or the input's chrome row) whose default is the org's `ai_connections.default_model`. v1 lists the models the connected provider (`claude`) offers; the selection is sent with the next send so `13` records it on the assistant `messages.model`. If `default_model` is null (not yet set in `[[../11-ai-connection-claude/spec|11]]`), fall back to a sensible default and surface a hint to set one. The switcher is presentation/UX — it never sends provider keys or an `org_id`; it sends only a model identifier the backend validates against the org's connection.
- **States — the unhappy paths are first-class.** Each renders on a **solid** surface, calm copy, no raw stack traces:
  - **Empty (no sessions):** a friendly first-run prompt ("faça sua primeira pergunta") with example questions; sending creates the first session.
  - **Empty (session, no messages):** the new-conversation invitation in the message area.
  - **Loading list / loading messages:** skeletons on solid surfaces (not a glass shimmer over data).
  - **Streaming:** a typing/"respondendo…" indicator on the assistant bubble; input locked.
  - **Out-of-scope question** (`13` decides the question can't be answered from exposed tables): a clear "não consigo responder isso com os dados conectados" assistant message, optionally suggesting what *is* answerable — not an error toast.
  - **Empty result** (query ran, zero rows): an explicit "nenhum dado encontrado para esse período/filtro" answer, distinct from an error.
  - **Client DB down** (`13` reports the client DB unreachable / connection `failed`): a non-alarming "não consegui acessar seu banco agora" with a link to the connection screen (`[[../10-connect-db-ui/spec|10]]`); does not blame the user.
  - **AI key failed/invalid** (`13` reports the AI call failed / key rejected): "houve um problema com a conexão da IA" with a link to the AI screen (`[[../11-ai-connection-claude/spec|11]]`).
  - **Gating (prerequisite missing):** if there is no `active` DB connection or no `active` AI connection, the chat is not usable — show a solid call-to-action pointing to `10`/`11` instead of an input that will only fail.
  - **Session expired (`401`):** defer to `06`'s global handler (clear `me`, redirect to `/login`); the chat does not invent its own auth handling.
- **Optimistic & reconciliation safety.** The optimistic user bubble and the streaming assistant bubble are clearly transient until reconciled; if the send mutation/stream fails before any token, roll back to a re-enabled input with the typed question preserved (don't lose the user's text). Never double-render a message after the messages query refetches (key by server id once known; use a stable temporary id before).
- **Accessibility.** The message list is a labeled log; new assistant content is announced politely (`aria-live="polite"`) without spamming on every token (announce on settle, not per chunk). The input is a real labeled control; Enter sends, Shift+Enter newlines; the send button has an accessible label. The model switcher and session menu are keyboard-operable with correct focus management. Visible focus rings and `prefers-reduced-motion` (typing indicator) are already in the CSS — respect them. Auto-scroll to the newest message, but don't trap a user who has scrolled up to read.
- **Best practices.** Follow `react-best-practices` + `vercel-react-best-practices`: TanStack Query for sessions/messages (no effect-driven fetching), a **stable** streaming consumer that doesn't re-subscribe on every render, memoized message rendering so a long conversation doesn't re-render wholesale per streamed token, lazy-load the chat route chunk, and keep components typed and prop-driven (`[[../../rules/use-best-practices-skills|use-best-practices-skills]]`). The client **never** constructs or sends an `org_id`/tenant id on any request (anti-IDOR, `[[../../constitution|Constitution]]`).
- **Testing (Vitest + React Testing Library).** Cover: sessions list renders org-scoped + `updated_at`-desc order; create/select/rename mutations update the cache and URL; selecting a session loads its messages on solid surfaces; **send → optimistic user bubble → incremental streamed assistant bubble → settle/invalidate**; the input locks during a stream and unlocks after; each unhappy path (out-of-scope, empty result, DB down, AI key failed, gating) renders its distinct solid-surface state; the model switcher defaults to `default_model` and sends the chosen model; a **glass-only-on-chrome assertion** that no `ChatBubble`/number/table/`MetricCard` is inside a `GlassPanel`/`.glass`; and that no request body/path ever carries an `org_id`. Mock `13`'s endpoints and stream; do not hit a real backend or client DB.

## User Stories / Scenarios

1. **First question, first session.** A newly-onboarded owner opens `/chat` with no conversations. They see a first-run prompt and example questions, type *"quanto vendi em maio?"*, and send. A session is created, their question appears instantly, and the assistant's answer streams in token by token, settling into *"Em maio você vendeu R$ 128.000, 12% a mais que abril."* on a solid bubble with the figure in `tabular-nums`. The new session appears at the top of the sidebar.
2. **Continue a conversation.** They click an existing session in the sidebar; the URL becomes `/chat/:id`, the message history loads on solid bubbles in `created_at` order, and they ask a follow-up that streams in below.
3. **Rename a session.** From the session's "…" menu they rename "Nova conversa" to "Vendas Q2"; the sidebar updates immediately (optimistic), persisted via the rename mutation, with order unchanged.
4. **Out-of-scope question.** They ask something the exposed tables can't answer; instead of a wrong number or a crash, the assistant bubble explains it can't answer that from the connected data and hints at what it *can* answer.
5. **Empty result.** They ask "quanto vendi em fevereiro?" for a month with no sales; the answer is an explicit "nenhum dado encontrado para fevereiro," visibly different from an error.
6. **Client DB is down.** Mid-use, the client's MySQL is unreachable; the next answer is a calm "não consegui acessar seu banco agora" with a link to the connection screen — not a red error, not a blamed user.
7. **AI key problem.** The Claude key is revoked/invalid; the assistant area shows "houve um problema com a conexão da IA" with a link to fix it in `[[../11-ai-connection-claude/spec|11]]`, and the input is re-enabled with the typed question preserved.
8. **Switch model.** They open the model switcher (defaulted from `ai_connections.default_model`), pick a different Claude model, and ask again; the next assistant message is produced by — and recorded as — the chosen model.
9. **Reload mid-conversation.** With `/chat/:id` open they refresh; the guard re-bootstraps the session, the sessions list and the selected conversation reload from the server, and they're back where they were — no lost state, no auth flash (handled by `06`).
10. **Gating.** A user who connected the DB but not the AI lands on the chat and sees a solid call-to-action to finish connecting Claude (`[[../11-ai-connection-claude/spec|11]]`), not a dead input.

## Success Criteria

- The chat mounts inside `06`'s protected shell as a two-pane layout; the sessions sidebar and chat input may be glass, and **every** message, number, table, and `MetricCard` renders on a solid surface — a reviewer can confirm no reading text or figure sits on glass.
- The sessions list shows the caller's sessions only, ordered `updated_at` desc; create, select (URL-driven, deep-linkable, reload-safe), and rename all work and keep the TanStack Query cache consistent. A successful send re-orders the active session to the top.
- Selecting a session loads its `messages` (user + assistant, `created_at` order) on solid `ChatBubble`/`Card` surfaces, figures in `tabular-nums`.
- Sending a question shows the user's message optimistically, then streams the assistant's answer incrementally from `[[../13-chat-orchestrator/spec|13]]`, settling into the persisted message and invalidating the messages query so server state is canonical; the input is locked during the stream and unlocked after; one in-flight stream per session.
- The model switcher defaults to `ai_connections.default_model`, lets the user pick another of the provider's models, sends the choice with the next message, and the answer is recorded under the chosen `messages.model`.
- All unhappy paths render distinct, calm, solid-surface states: out-of-scope, empty result, client DB down (→ link to `10`), AI key failed (→ link to `11`), gating when a prerequisite connection is missing, and a clean not-found for an unknown `session_id`. None show a raw error or a stuck spinner.
- No request ever carries an `org_id`/tenant id; `session_id` is the only conversation identifier the client sends, and the backend re-scopes it by the cookie's `org_id`.
- The message log is accessible: `aria-live="polite"` announces settled assistant answers (not per token), Enter sends / Shift+Enter newlines, the switcher and session menu are keyboard-operable, focus and reduced-motion are respected, and auto-scroll doesn't trap a user reading scrollback.
- Vitest + RTL suite (list ordering/scoping, create/select/rename, message load, the full send→stream→settle path, input lock, every unhappy path, switcher default/selection, the glass-only-on-chrome assertion, and the no-`org_id` assertion) is green; lint and `type-check` pass with `strict: true`.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| An answer, number, or table is rendered inside a `GlassPanel`/`.glass`, breaking the product's precision/legibility promise | Constrain glass to the sessions sidebar, the input, and menus only; render every bubble/table/`MetricCard` on solid surfaces; add an RTL test asserting no data node is under `.glass` (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`, `[[../../constitution|Constitution]]`) |
| The client constructs or sends an `org_id` to fetch "a session," reopening IDOR | Send only `session_id`; rely on `13` to scope by the cookie's `org_id`; test that no request body/path includes a tenant id; never read an org id into client state |
| Streaming re-renders the whole conversation on every token, janking long chats | Memoize message rows; isolate the streaming bubble's state; keep the streaming consumer stable (no re-subscribe per render) per `vercel-react-best-practices`; announce on settle, not per chunk |
| Optimistic user/assistant bubbles desync or duplicate when the messages query refetches | Use stable temporary ids pre-persist, reconcile to server id on `done`, then invalidate the messages query so server state is canonical; key by id to prevent double-render |
| Unhappy paths (out-of-scope, empty result, DB down, AI key failed) are collapsed into one generic "error," confusing the owner | Treat each as a distinct, typed state from `13` with its own calm copy and (where relevant) a link to `10`/`11`; cover each with a test; empty-result is explicitly *not* an error |
| A stream error leaves a half-written assistant bubble stuck on screen | On stream error replace the partial bubble with the matching state and re-enable the input with the question preserved; never persist or keep a partial as if it were an answer |
| Model switcher drifts from `ai_connections.default_model` or sends an unsupported model | Source the default from the connection; list only the provider's models; let `13` validate the model against the org's connection and reject unknowns; default sensibly when `default_model` is null |
| Chat is shown when no `active` DB/AI connection exists, producing only failures | Gate the input behind connection readiness; when a prerequisite is missing, show a solid CTA to `10`/`11` instead of a doomed input |
| `useEffect`+`fetch` for sessions/messages causes waterfalls and races | Use TanStack Query for all non-stream reads/mutations; reserve the streaming client strictly for the live answer; keep `QueryClient` and the fetch wrapper (from `06`) stable (`react-best-practices`) |

## Open Questions

- [NEEDS CLARIFICATION: `[[../13-chat-orchestrator/spec|13]]`'s streaming transport and event shape] — SSE vs. the Vercel AI SDK data-stream protocol, and how `done`, the persisted `message_id`/`model`, and each unhappy-path outcome (out-of-scope / empty-result / db-down / ai-failed) are signaled in-band so the UI can switch states deterministically. Default lean: consume the AI SDK's stream protocol with a typed terminal event carrying the persisted message and an outcome discriminator.
- [NEEDS CLARIFICATION: session creation timing] — does sending the first message in `/chat` (no id) create the `chat_sessions` row server-side and return its id (then the client routes to `/chat/:id`), or does the client create an empty session first? Default lean: first send creates the session and returns its id; client navigates on receipt — avoids empty orphan sessions.
- [NEEDS CLARIFICATION: session title source] — is `chat_sessions.title` auto-derived from the first question (and by whom — `13` or the client) or always user-set, with "Nova conversa" as the placeholder until renamed? Default lean: placeholder title on create, optional auto-title from the first question by `13`, user rename always wins.
- [NEEDS CLARIFICATION: how a structured/tabular answer is delivered] — does `13` return tabular results as structured data (rows/columns the client renders into a solid `Card` table with `tabular-nums`) or only as formatted text in `messages.content`? Default lean: support a structured payload alongside the text so tables render as real, aligned tables on a solid surface; fall back to text when absent.
- [NEEDS CLARIFICATION: model list source] — does the model switcher get its candidate models from `[[../11-ai-connection-claude/spec|11]]`/`13` (an endpoint returning the provider's available models) or a static client-side list pinned to the provider? Default lean: a small backend-provided list scoped to the connected provider, defaulting to `ai_connections.default_model`.
- [NEEDS CLARIFICATION: stop/cancel a streaming answer] — should the user be able to abort an in-flight stream, and does `13` support cancellation (and still persist a partial)? Default lean: provide a stop control that aborts the client stream; persistence of partials follows `13`'s capability — if unsupported, the aborted answer is discarded, not saved.
