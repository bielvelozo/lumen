# Web Shell & Auth UI — Spec

**Status:** Draft
**Scope:** The Flow 1 frontend in `apps/web`: port the design system into the app, render `<AppBackground />` and wire theme, set up React Router (public auth routes + a protected glass app-shell), configure TanStack Query for cookie auth, build the auth pages (signup, login, verify-email landing, forgot/reset password), and add a protected-route guard that bootstraps the session via `/auth/me`.

## Context

This is the first real screen the product ever shows and the entire client-side surface for Flow 1 (signup → verify → login). The scaffold (`[[../00-monorepo-scaffold/spec|00]]`) left `apps/web` as an empty-but-runnable Vite + React + TypeScript SPA that only imports the design-system CSS to prove the pipeline; it deliberately deferred Router, TanStack Query, and the design-system port to here. This spec makes `apps/web` a navigable, themed, authenticated application shell with working auth forms.

The backend halves of Flow 1 are owned by neighbors and are **called**, not implemented, here: signup (`[[../03-signup-and-org/spec|03]]`, `POST /auth/signup`), email verification (`[[../04-email-verification/spec|04]]`, the verify + resend endpoints and the link token), and login / JWT sessions / `/auth/me` / refresh / logout (`[[../05-login-jwt-sessions/spec|05]]`). The request/response Zod contracts for these live in `packages/shared` and are the single source the forms validate against — no duplicated shapes on the client.

Two invariants from `[[../../constitution|Constitution]]` shape every decision here. **Cookie-only auth (anti-IDOR):** the JWT lives in an httpOnly/Secure/SameSite=None cookie the frontend can never read; the `org_id` is derived server-side from that cookie, so the client never holds, sends, or even knows a tenant id. **Glass only on chrome** (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`): the frosted-glass treatment appears only on the sidebar, topbar, menus, and chat field — every number, table, or reading-length text sits on a solid, high-contrast surface. Both are non-negotiable. All React work follows `react-best-practices` + `vercel-react-best-practices` per `[[../../rules/use-best-practices-skills|use-best-practices-skills]]`.

## Problem Statement

There is no UI. A new owner has no way to create an account, confirm their email, or log in, and an authenticated user has no frame to live inside. We need: (1) the design system moved into `apps/web` as typed `.tsx` so screens can be built from `AppBackground`, `ThemeToggle`/`useTheme`, `GlassPanel`, `Card`, `MetricCard`, `TextField`, `ChatBubble`, `NavItem`, `Avatar`, and `Button`; (2) a routing structure that cleanly separates **public** auth routes from a **protected** app shell, with a guard that decides which a visitor may see by asking the server (`/auth/me`) — because the auth cookie is invisible to JS, session state cannot be read locally and must be bootstrapped; (3) a query/mutation layer configured to send the cookie on every request (`credentials: 'include'`) and to treat a `401` as "not authenticated" rather than a crash; and (4) the four auth surfaces themselves — signup, login, a verify-email landing that consumes the `?token=` from the email link, and forgot/reset password — each validating against the shared Zod contracts and rendering server errors without leaking which emails exist.

## Non-Goals

- **The auth/session backend.** Endpoints, JWT signing, cookie issuance, token hashing, email sending, and `org_id` derivation are `[[../03-signup-and-org/spec|03]]`, `[[../04-email-verification/spec|04]]`, `[[../05-login-jwt-sessions/spec|05]]`. This spec only calls them.
- **Connect-DB screens** — the consent/terms, onboarding-script, and connection-state UI are `[[../10-connect-db-ui/spec|10]]`.
- **AI-connect screen** — pasting/validating the Claude key is `[[../11-ai-connection-claude/spec|11]]`.
- **Chat UI** — the conversation surface, streaming, and message list are `[[../14-chat-ui/spec|14]]`. Here the protected shell renders a placeholder home, not the chat.
- **A real dashboard / metrics.** `MetricCard` may appear on a placeholder home only as a static illustration of the data surface; no live data, no queries against the client DB.
- **i18n framework.** Copy is written in Portuguese (the product's language) inline; no extraction/translation layer yet.
- **Design-token changes.** The CSS tokens and component visuals are taken as-is from `design-system/`; this spec ports, it does not redesign.

## Constraints

- **Design-system port.** Move `design-system/design-system.css` into `apps/web/src/design-system/` and import it **exactly once** at the entrypoint (`main.tsx`). Convert `design-system/ui.jsx` to typed `src/design-system/ui.tsx` (or split per component), preserving the exported surface — `useTheme`, `ThemeToggle`, `AppBackground`, `GlassPanel`, `Button`, `Card`, `MetricCard`, `TextField`, `ChatBubble`, `Avatar`, `NavItem` — with explicit prop types (e.g. `Button` `variant: 'primary' | 'ghost'`, `MetricCard` `trend: 'up' | 'down'`, `ChatBubble` `from: 'me' | 'them'`, `GlassPanel` polymorphic `as`). `<AppBackground />` is rendered **once** at the tree root so glass has something to refract. `Showcase` may be ported behind a dev-only route or dropped.
- **Theme.** `useTheme` persists to `localStorage` and sets `data-theme` on `<html>` (existing behavior); `<ThemeToggle />` toggles it. Initial theme respects a saved value, else `prefers-color-scheme`. Theme must apply before first paint where practical to avoid a flash. Replace the component's hardcoded `aria-label` strings only if switching copy conventions; otherwise keep accessible labels.
- **Routing (React Router).** A single router with two zones:
  - **Public** (redirect to the app home if already authenticated): `/signup`, `/login`, `/verify-email`, `/forgot-password`, `/reset-password`. These render on a centered, focused auth layout (logo + a solid `Card` for the form; glass only as incidental chrome, never under the form fields’ reading text).
  - **Protected** (redirect to `/login` if not authenticated): an app-shell layout with a **glass** sidebar (`NavItem`s) + **glass** topbar (`ThemeToggle`, `Avatar`, account menu) wrapping an `<Outlet />`. The placeholder home and all later app routes (`10`, `11`, `14`) mount inside it.
  - Use a layout-route + guard pattern (loader-or-component guard) so the protected layout is the single choke point; deep links to protected routes while unauthenticated land on `/login` and ideally return there after login (`?from=`).
- **Session bootstrap & guard.** Because the JWT cookie is httpOnly, the client cannot read auth state. On load, the guard issues `GET /auth/me` (`credentials: 'include'`): `200` → authenticated (cache the returned user/org-display profile in TanStack Query); `401` → unauthenticated. While the bootstrap query is pending, show a minimal splash, **not** a flash of the login page or of protected content. Never infer auth from `localStorage` or a JS-readable flag — the server is the source of truth.
- **TanStack Query for cookie auth.** One `QueryClient` at the root. A shared fetch wrapper sets `credentials: 'include'`, `Content-Type: application/json`, and a JSON error envelope parser on **every** request; the base URL comes from a validated env var (`VITE_API_URL`). A global handler treats `401` as "logged out" (clear the `me` cache, redirect to `/login`), not as a thrown error toast. Sensible defaults: no aggressive refetch storms (`react-best-practices`), `retry: false` on `401`, `me` query with conservative `staleTime`. The client **never** constructs or sends an `org_id` / tenant id in any request (anti-IDOR, `[[../../constitution|Constitution]]`).
- **Auth forms — validation & contracts.** Each form validates with the **shared Zod schemas** from `packages/shared` (the same ones `03`/`04`/`05` use server-side) via a form library or a thin `zodResolver`-style hook; client validation is UX only, never the security boundary. Map field-level `400` errors back onto inputs. Disable submit while pending; show inline, accessible error and success states.
  - **Signup** (`POST /auth/signup`): `{ email, password, organizationName }`. On success show the "check your email" state (`03` issues no session, so there is **no** auto-login and no redirect into the app). Honor `03`'s non-enumerating duplicate-email response — render the same success-shaped UI whether or not the email already existed; the UI must not reveal account existence.
  - **Login** (`05`): `{ email, password }` → on `200` the server sets the cookie; the client then refetches `/auth/me` and routes to `?from=` or the home. Invalid credentials show a single generic "e-mail ou senha inválidos" (no enumeration). Surface an "email not verified" path if `05` distinguishes it (offer resend via `04`).
  - **Verify-email landing** (`/verify-email`): read the raw `token` from the URL query (the link in `04`'s email), POST it to `04`'s verify endpoint, and show pending / success (→ CTA to `/login`) / invalid-or-expired (→ offer resend) states. The raw token exists only in the URL and is sent once; it is never stored.
  - **Forgot password** (`/forgot-password`): `{ email }` → always render a uniform "if an account exists, we sent a link" message (non-enumerating, matching `03`/`04` posture). **Reset password** (`/reset-password`): read `token` from the URL, collect a new password (validated against the shared policy), POST to the reset endpoint, show success → `/login` or invalid/expired → re-request.
- **Glass-only-on-chrome (enforced).** Glass (`GlassPanel`/`.glass`) only on sidebar, topbar, menus/popovers, and the (later) chat field. Auth form fields, validation/error text, the verify/reset result messages, and any `Card`/`MetricCard` content sit on solid surfaces. Reading text uses Inter on solid; `Space Grotesk` only for brand/titles. No number or reading-length text is ever placed on glass (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`, `[[../../constitution|Constitution]]`).
- **Accessibility.** Forms are real `<form>`s with labeled inputs, `aria-invalid`/`aria-describedby` on errored fields, focus moved to the first error on submit, visible focus rings (already in the CSS), and `prefers-reduced-motion` respected (already in the CSS). The shell is keyboard-navigable; the account menu traps/returns focus correctly.
- **Best practices.** Follow `react-best-practices` + `vercel-react-best-practices`: avoid needless re-renders and effect-driven data fetching (use TanStack Query, not `useEffect`+`fetch`), keep the fetch wrapper and `QueryClient` stable, lazy-load route chunks where it helps, and keep components typed and prop-driven (`[[../../rules/use-best-practices-skills|use-best-practices-skills]]`).
- **Testing (Vitest + React Testing Library).** Cover: guard redirects (unauth → `/login`, auth → home, splash-not-flash during bootstrap), each form's happy path + validation errors + server-error mapping, the non-enumerating signup/forgot copy, the verify-email landing consuming a URL token across its three states, and that the fetch wrapper always sends `credentials: 'include'` and never sends an `org_id`. Mock the API; do not hit a real backend.

## User Stories / Scenarios

1. **A visitor signs up.** An owner opens `/signup`, fills `{ email, password, organizationName }` (validated live against the shared schema), submits, and lands on a "check your email" confirmation. No session is created and the app does not let them in yet. If the email already existed, the screen looks identical — no tell.
2. **They verify their email.** They click the link in the email and arrive at `/verify-email?token=…`. The page consumes the token, shows a brief pending state, then "e-mail verificado" with a CTA to log in. An expired/invalid token instead shows an error with a "resend link" action.
3. **They log in.** At `/login` they enter their credentials; on success the server sets the cookie, the app refetches `/auth/me`, and they land inside the protected shell (or back at the page they originally deep-linked to). Wrong credentials show one generic, non-enumerating error.
4. **Returning user, live session.** A user with a valid cookie opens the app at `/`. The guard's `/auth/me` returns `200` during a short splash; they go straight to the protected home inside the glass shell, theme restored from `localStorage`, no login flash.
5. **Unauthenticated deep link.** A logged-out user opens a protected URL directly. The guard's `/auth/me` returns `401`; they are redirected to `/login?from=…` and, after logging in, returned to where they were headed.
6. **Session expires mid-use.** A request comes back `401` (cookie expired/cleared); the global handler clears the `me` cache and routes them to `/login` without a crash or a stuck spinner.
7. **They reset a forgotten password.** From `/forgot-password` they submit their email and always see the same "if an account exists, we sent a link" message. The emailed link opens `/reset-password?token=…`, they set a new password (validated), and on success are sent to `/login`.
8. **They toggle theme.** Anywhere in the app, the `ThemeToggle` flips light/dark; `data-theme` updates on `<html>`, the choice persists, and it survives reload — including on the public auth screens.

## Success Criteria

- The design system lives in `apps/web/src/design-system/` as typed `.tsx`, the CSS is imported once in `main.tsx`, every original export is preserved with explicit prop types, and `<AppBackground />` renders once at the root.
- `useTheme`/`<ThemeToggle />` set `data-theme` on `<html>`, persist to `localStorage`, honor `prefers-color-scheme` on first load, and survive reload with no flash of the wrong theme.
- React Router serves the public routes (`/signup`, `/login`, `/verify-email`, `/forgot-password`, `/reset-password`) and a protected app-shell layout (glass sidebar + glass topbar) with a placeholder home behind it.
- The protected-route guard bootstraps via `GET /auth/me`: `200` admits to the shell, `401` redirects to `/login?from=…`, and the pending state shows a splash — never a flash of login or protected content. Authenticated users hitting a public route are redirected to home.
- A single `QueryClient` + shared fetch wrapper send `credentials: 'include'` on every request, read the API base from `VITE_API_URL`, and convert a `401` into a clean logged-out redirect; no request ever carries an `org_id` or tenant id.
- All four auth surfaces work end-to-end against mocked `03`/`04`/`05` endpoints, validate against the shared Zod contracts, map field-level `400`s onto inputs, and render non-enumerating copy for signup duplicate-email and forgot-password.
- The verify-email landing consumes the raw `?token=` from the link, posts it once, and correctly renders pending / verified / invalid-or-expired (with resend) — without persisting the token anywhere.
- Glass appears only on chrome (sidebar, topbar, menus); every form, error message, result screen, and `Card`/`MetricCard` sits on a solid surface. A reviewer can confirm no reading text renders on glass.
- Forms are accessible (labeled inputs, `aria-invalid`/`aria-describedby`, focus-to-first-error, visible focus, reduced-motion honored).
- Vitest + RTL suite (guard redirects, splash-not-flash, each form's happy/validation/server-error paths, non-enumerating copy, verify-email token flow, and `credentials: 'include'` / no-`org_id` assertions) is green; lint and `type-check` pass with `strict: true`.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The httpOnly cookie is unreadable by JS, so naive "read auth from `localStorage`" patterns leak a false session or flash the wrong screen | Make `/auth/me` the single source of truth; gate the whole tree on its result; show a splash while pending; never store an auth flag client-side |
| A reading-length error/result message or a `MetricCard` is placed on a `GlassPanel`, violating glass-only-on-chrome | Constrain glass to sidebar/topbar/menus in the shell layout; put every form/result/`Card` on solid surfaces; add a test/review check that no data text lands on glass (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`) |
| Client form validation drifts from server validation, or is mistaken for the security boundary | Import the **same** Zod schemas from `packages/shared`; treat client checks as UX only; always map and trust the server's `400` field errors |
| Auth UI re-introduces user enumeration the backend worked to avoid (distinct copy/timing for "email exists") | Mirror `03`/`04`'s non-enumerating posture: identical success-shaped UI for signup duplicate and forgot-password; one generic login error; no existence tells |
| `useEffect`+`fetch` data fetching causes waterfalls, races, and re-render storms | Use TanStack Query for `me`/mutations per `react-best-practices`/`vercel-react-best-practices`; keep `QueryClient` and the fetch wrapper stable; disable retry on `401` |
| Cross-site cookie (`SameSite=None; Secure`) is dropped because the client doesn't send credentials or the API base/CORS is misconfigured | Centralize `credentials: 'include'` in one fetch wrapper used everywhere; drive the API base from `VITE_API_URL`; verify the cross-origin cookie round-trips in an integration check |
| The raw verify/reset token in the URL is logged, persisted, or re-sent | Read it from the query once, POST it, and discard; never write it to storage; strip it from history where practical |
| Converting `ui.jsx` → `.tsx` silently changes a component's class output or prop surface, breaking the visual contract | Preserve exact class names and exported props; add explicit prop types without altering rendered markup; smoke-test `Showcase`/`MetricCard`/`GlassPanel` rendering |
| A flash of unstyled/wrong-theme content before `data-theme` is applied | Apply the persisted theme as early as possible (inline pre-paint set or root effect ordered before first meaningful paint); test reload preserves theme |

It must **not** include anything the client could use as a tenant id in a request. Default lean: a minimal `{ displayName, email, orgName }` for presentation only.
- [NEEDS CLARIFICATION: does `[[../05-login-jwt-sessions/spec|05]]` distinguish "wrong credentials" from "email not verified" on login?] — if yes, the login form needs an "unverified → resend" branch (via `[[../04-email-verification/spec|04]]`); if no, everything funnels into one generic error. Default lean: distinguish only enough to offer resend, without enumerating.
- [NEEDS CLARIFICATION: post-login redirect policy] — honor a `?from=` deep link, or always land on the home? And cap it to in-app paths to avoid open-redirect abuse. Default lean: honor `?from=` restricted to same-origin app routes, else home.
- [NEEDS CLARIFICATION: route-mode and data-loading strategy in React Router] — use loaders/`createBrowserRouter` for the guard vs. a component-level guard wrapping `<Outlet />`? Default lean: a layout-route guard component backed by the `me` query, to keep the bootstrap query the single choke point.
- [NEEDS CLARIFICATION: are signup, forgot-password, and verify-resend rate-limited / bot-protected on the client side at all] — likely a backend/cross-cutting concern, but flag whether the UI needs a captcha or cooldown affordance. Default lean: defer to the backend; reserve UI space for a cooldown message on resend.
- [NEEDS CLARIFICATION: copy language and tone] — Portuguese is assumed throughout; confirm there is no near-term need for an i18n layer before strings proliferate. Default lean: inline pt-BR copy now, no framework.
