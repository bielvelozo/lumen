# Connect-DB UI — Spec

**Status:** Draft
**Scope:** The entire Flow 2 frontend in `apps/web` — a guided, multi-step wizard that walks the owner from **consent** → **onboarding script** → **credential form** → **live connection test** → **introspection + table/relationship exposure** → a durable **connection status dashboard** to review, re-test, and edit later. It is UI only: it *calls* the backends owned by `[[../07-db-connection-consent-and-script/spec|07]]`, `[[../08-db-connection-create-and-test/spec|08]]`, and `[[../09-introspection-and-exposure/spec|09]]`, drives all server state through TanStack Query, and renders every piece of data on solid surfaces with glass confined to the shell chrome.

## Context

This is the second flow the product ships and the screen where an owner actually points the assistant at their database. It lives inside the protected app shell built in `[[../06-web-shell-and-auth-ui/spec|06]]` — glass sidebar + glass topbar wrapping an `<Outlet />`, the cookie-auth fetch wrapper, the `QueryClient`, and the ported design system (`AppBackground`, `GlassPanel`, `Card`, `TextField`, `Button`, etc.). Flow 2's backend is already cut into three neighbors that this spec consumes and never re-implements: consent + the read-only onboarding script (`[[../07-db-connection-consent-and-script/spec|07]]`), create-or-update + encrypt + live test driving `pending → active | failed` (`[[../08-db-connection-create-and-test/spec|08]]`), and schema introspection + `exposed_tables`/`exposed_relationships` selection (`[[../09-introspection-and-exposure/spec|09]]`).

Three things shape every decision here. **Connection state is first-class, not inferred** — the schema carries `status` (`pending`/`active`/`failed`), `last_tested_at`, and a sanitized `last_error` on `db_connections`; this UI is a faithful mirror of that state, never a client-side guess at it. **Anti-IDOR (`[[../../constitution|Constitution]]` invariant 1)** — the org is derived server-side from the JWT cookie; the frontend never holds, constructs, or sends an `org_id` or a `db_connections.id` to scope a request (v1 is one connection per org, so the server already knows which row "mine" means). **Glass only on chrome (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`, invariant 6)** — the onboarding script, the credential form, the discovered tables/columns/FKs, status badges, and error text are all *data the owner reads exactly*; they sit on solid, high-contrast surfaces, with glass only on the surrounding frame. All React work follows `react-best-practices` + `vercel-react-best-practices` per `[[../../rules/use-best-practices-skills|use-best-practices-skills]]`.

## Problem Statement

A logged-in owner has a frame to live in but no way to connect their database. The journey is genuinely multi-step and stateful: they must accept terms before any credential exists, get and run a least-privilege script on *their* server, hand us coordinates that may or may not work, watch a live test resolve, then choose — from their real schema — exactly which tables and relationships the assistant may ever see. Each step has unhappy paths (stale consent, a failed test with only a sanitized error to show, an introspection that found nothing, a relationship whose endpoints aren't both exposed) that must be legible rather than dead ends. We need a wizard that: resumes at the right step from the server's connection state on every load (never from local memory); renders the script and all schema data on solid surfaces for exact reading/copying; submits each step to its owning backend via TanStack Query mutations and reflects `pending`/`active`/`failed` directly; enforces *client-side* the invariant that an approved relationship's `from_table` and `to_table` are both selected (a UX guard, never the security boundary); and finally settles into a status dashboard the owner can return to in order to re-test, re-introspect, or edit the exposure set — all without ever sending a tenant id.

## Non-Goals

- **Any backend logic.** Consent persistence + the script generator (`[[../07-db-connection-consent-and-script/spec|07]]`), create/encrypt/test + the connection state machine (`[[../08-db-connection-create-and-test/spec|08]]`), and introspection + exposure persistence with its server-side endpoint-both-exposed validation (`[[../09-introspection-and-exposure/spec|09]]`) are *called*, not built. No SQL, no encryption, no live MySQL connection runs in this spec.
- **The AI-connect UI** — pasting/validating the Claude key and choosing the default model is `[[../11-ai-connection-claude/spec|11]]`.
- **Chat** — the conversation surface, streaming, and message list are `[[../14-chat-ui/spec|14]]`.
- **The auth shell, router, theme, fetch wrapper, and design-system port** — all owned by `[[../06-web-shell-and-auth-ui/spec|06]]`; this spec mounts inside that shell and reuses its primitives.
- **Generating or storing the password client-side.** The owner types it into the credential form and it is sent once to `08`; the UI never persists, echoes back, or re-displays it. The onboarding script tells the owner to choose their own password locally (`[[../07-db-connection-consent-and-script/spec|07]]`).
- **Column-level exposure.** v1 exposes at the table level (plus introspection) per `[[../../constitution|Constitution]]` scope guardrails; columns are *displayed* for context, not individually toggled.
- **Multiple connections / non-MySQL engines.** One MySQL connection per org in v1; the UI assumes a single "my connection".
- **The legal terms copy and the script template text.** Sourced from `07`; this spec renders whatever `07` returns and pins the `consent_version` it showed.

## Constraints

- **Lives in the protected shell.** A route group under the protected layout from `[[../06-web-shell-and-auth-ui/spec|06]]` (e.g. `/connect/database/*` or a `/settings/database` area), reachable from a sidebar `NavItem`. Unauthenticated access is already handled by `06`'s guard. Lazy-load the route chunk where it helps (`react-best-practices`).
- **Server state via TanStack Query, exclusively.** The connection (`status`, `last_tested_at`, sanitized `last_error`, exposure set) is fetched with a query (e.g. `GET` "my db connection"); consent, create-and-test, re-test, introspect, and save-exposure are **mutations** that invalidate that query on success. No `useEffect`+`fetch`; no derived auth/connection state in `localStorage`. The fetch wrapper from `06` already sends `credentials: 'include'` and never carries an `org_id`. Use sensible defaults: `retry: false` on `4xx`, conservative `staleTime`, no refetch storms.
- **The wizard resumes from server state, not local memory.** On entering Flow 2 the connection query decides the step: no consent (or stale `consent_version`) → consent gate; consent but no row / `pending` → script + credential form; `failed` → test-result step showing the sanitized `last_error` with a retry; `active` but no/empty exposure → introspection + exposure picker; `active` with a saved exposure set → the status dashboard. A deep link to a later step while an earlier gate is unmet redirects back to the unmet gate. The current step is derived from data, never from a stashed client flag.
- **Step 1 — Consent.** Render the plain-language terms text and `consent_version` returned by `[[../07-db-connection-consent-and-script/spec|07]]` on a **solid** `Card`; an explicit Accept action posts the acceptance (org + user derived server-side; the body carries no org id). The four scope points (read-only access, owner chooses tables, secrets encrypted at rest, revocable) must be visible before Accept is enabled. If terms moved to a newer version since a prior acceptance, show the new text and require re-acceptance (mirrors `07` scenario 5).
- **Step 2 — Onboarding script.** Display the server-generated MySQL `CREATE USER` + `GRANT SELECT` script from `07` in a **solid code panel** (monospace, high contrast — never on glass; it must be copied exactly), with a **copy-to-clipboard** button that confirms the copy. Pair it with concise instructions: run it on your own MySQL server, it creates a dedicated **read-only** user, choose your own strong password locally, never give us root. If `07` accepts an optional database name to scope the grant, collect it here and reflect it in the rendered script.
- **Step 3 — Credential form.** Collect `host`, `port`, `database`, `username`, `password`, and an **SSL toggle** (`ssl_enabled`, default on), validated client-side against the **shared Zod schema** from `packages/shared` that `[[../08-db-connection-create-and-test/spec|08]]` uses server-side (host non-empty, port `1..65535`, names non-empty) — client validation is UX only, never the security boundary. The password field is write-only: masked, never pre-filled, never read back from the server. Submitting calls `08`'s create-or-update + test in one action; the body carries config only, never an `org_id`/connection id.
- **Step 4 — Connection test state.** Render `08`'s outcome straight from the connection's first-class state on a **solid** surface: a `pending`/testing spinner while the mutation is in flight, then `active` (success badge + `last_tested_at`) or `failed` (error badge + the **sanitized** `last_error` category, e.g. "authentication failed", "host unreachable", "SSL error", "database not found"). Never invent or embellish an error beyond what `08` returns; never display a raw driver string (the backend already guarantees only safe categories reach the client). Provide a **retry** that re-runs the test — re-test must work without re-entering the password (`08` decrypts the stored secret). Surface `08`'s over-privileged/root **read-only warning** prominently if present, without blocking per `08`'s chosen policy.
- **Step 5 — Introspection + exposure picker.** Trigger `[[../09-introspection-and-exposure/spec|09]]`'s introspection (only available once `active`) and render the discovered **tables, their columns (name + type), and foreign keys** on **solid** surfaces — a selectable table list, each table expandable to show its columns; relationships shown as `from_table.from_column → to_table.to_column`. The owner selects `exposed_tables` and approves `exposed_relationships`. **Enforce client-side** that a relationship can only be approved when *both* its `from_table` and `to_table` are selected: disable/auto-deselect a relationship whose endpoints aren't both exposed, with a clear inline reason — this mirrors and front-runs `09`'s server-side both-exposed validation (the server remains the authority; the client guard is UX). Saving posts the chosen `exposed_tables` + `exposed_relationships` to `09` and invalidates the connection query. Handle the empty-introspection case (no tables found / permission too narrow) with a legible message and a path back to re-test or fix the credential.
- **Step 6 — Connection status dashboard.** Once a connection exists, a durable review surface (the landing state when re-entering Flow 2 with an `active`, configured connection) showing: the non-secret config (`host`, `port`, `database`, `username`, SSL — **never** the password), the current `status` badge + `last_tested_at` + any sanitized `last_error`, the set of exposed tables/relationships, and actions to **re-test**, **re-introspect / edit exposure**, and **edit config** (re-opening step 3; an unchanged password is kept by `08`, so the field stays blank and optional on edit). Editing config that changes coordinates re-enters the test flow.
- **State-driven, accessible status UI.** Status badges, spinners, and error/warning banners are derived purely from the connection query data and are real, labeled, accessible elements (`aria-live` for the test result transition, `aria-busy` while testing, focus moved to the result). Disable mutation triggers while their mutation is pending; show inline pending/success/error states; map any field-level `400` from `08` back onto the credential inputs.
- **Glass-only-on-chrome (enforced).** Glass appears only on the shell sidebar/topbar/menus from `06`. The script panel, credential form, test-result panel, introspection tables/columns/FK lists, status badges, exposure selections, and all error/warning text sit on **solid** surfaces. No number, schema name, error string, or reading-length instruction is ever placed on glass (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`, `[[../../constitution|Constitution]]`). Data text uses Inter on solid; `Space Grotesk` only for titles/brand.
- **Best practices.** Follow `react-best-practices` + `vercel-react-best-practices`: TanStack Query for all server state (no effect-driven fetching), stable `QueryClient`/wrapper, typed prop-driven components, avoid re-render storms when expanding many tables/columns (virtualize or paginate a large schema list if needed), lazy-load the route, and keep the wizard a derived state machine rather than a tangle of booleans (`[[../../rules/use-best-practices-skills|use-best-practices-skills]]`).
- **Testing (Vitest + React Testing Library).** Cover: step derivation from connection state (each `status`/exposure combination routes to the right step; deep-link-to-locked-step redirects to the unmet gate); consent gate enabling Accept only after terms shown, and re-acceptance on a newer `consent_version`; script panel copy-to-clipboard and that it renders on a solid surface; credential-form Zod validation, masked write-only password, and `400` field-error mapping; test-result rendering of `active`/`failed` + sanitized `last_error` and a retry that doesn't re-prompt for the password; the relationship both-endpoints-selected client guard (a relationship auto-disables when an endpoint is deselected); save-exposure invalidating the connection query; the status dashboard never rendering the password; and that no request ever carries an `org_id`/connection id. Mock the `07`/`08`/`09` endpoints; never hit a real backend or MySQL.

## User Stories / Scenarios

1. **Owner accepts the terms.** A logged-in owner with no connection enters Flow 2, reads the four scope points on a solid card, and clicks Accept. The acceptance is recorded server-side (org + user derived from the JWT), and the wizard advances to the onboarding script.
2. **Owner runs the read-only script.** They see the `CREATE USER` + `GRANT SELECT` script on a solid code panel, copy it with one click (with a confirmation), and the instructions tell them to run it on their own server, pick their own password, and never use root. They create a dedicated read-only user on their MySQL.
3. **Owner submits credentials.** They fill `host`, `port`, `database`, `username`, `password`, and leave SSL on. Client validation catches a bad port before submit. On submit, the create-and-test call runs; the password is sent once and never echoed back.
4. **Test succeeds.** The test panel shows a brief testing state, then an `active` badge with `last_tested_at`. If `08` returns an over-privileged warning, it's shown prominently but doesn't block. The wizard moves on to introspection.
5. **Test fails, then retries.** A wrong password yields a `failed` badge with a sanitized "authentication failed" message (never a raw driver string). The owner fixes the credential and clicks Retry; the re-test runs against the stored connection without re-pasting the password and resolves to `active`.
6. **Owner picks exposed tables and relationships.** Introspection lists the real tables, their columns/types, and FKs on solid surfaces. The owner selects three tables and approves the `orders → products` relationship. They try to approve a relationship whose `to_table` isn't selected; the UI disables it with an inline "select both tables first" reason. They save; the exposure set persists and the wizard settles into the status dashboard.
7. **Deselecting an endpoint disables its relationship.** With a relationship approved, the owner deselects one of its tables; the previously-approved relationship is automatically deselected/disabled with a visible reason, keeping the selection consistent before save.
8. **Returning owner reviews and re-tests.** Days later the owner re-enters Flow 2 with an `active` connection and lands on the status dashboard: config (no password), `active` badge, `last_tested_at`, exposed tables/relationships, and actions. They click Re-test; the connection re-validates and the badge/`last_tested_at` update.
9. **Owner edits exposure.** From the dashboard they open "edit exposure", re-introspect (or reuse the discovered schema), change which tables are exposed, and save — fixing up any now-orphaned relationships via the both-endpoints guard before the save is allowed.
10. **Terms changed since acceptance.** An owner who accepted `v1` returns after terms moved to `v2`; the wizard detects the stale `consent_version`, shows the new terms, and requires re-acceptance before any further step.
11. **Empty or too-narrow schema.** Introspection returns no tables (or the read-only user can't see any). The picker shows a legible empty-state explaining the likely cause and offering a path back to re-test or fix the credential, rather than a blank screen.

## Success Criteria

- Flow 2 lives inside the protected shell from `[[../06-web-shell-and-auth-ui/spec|06]]`, reachable from the sidebar, with no auth/router/theme/fetch-wrapper re-implementation.
- The wizard's current step is **derived from the server's connection state** on every load (consent presence/version, row existence, `status`, exposure set) — never from a client-stored flag — and a deep link to a locked step redirects to the unmet gate.
- All server state flows through TanStack Query: one connection query plus mutations for consent, create-and-test, re-test, introspect, and save-exposure, each invalidating the connection query on success; `4xx` doesn't retry; no `useEffect`+`fetch`.
- The consent step shows `07`'s terms + `consent_version` on a solid surface, enables Accept only after the four scope points are shown, posts an org-/user-scoped acceptance with no org id in the body, and forces re-acceptance on a newer version.
- The onboarding script renders on a **solid** code panel with working copy-to-clipboard and read-only/own-password/never-root instructions — verifiably not on glass.
- The credential form collects `host`/`port`/`database`/`username`/`password`/SSL, validates against the **shared Zod schema**, keeps the password masked and write-only (never pre-filled or read back), submits to `08` with config only (no `org_id`/connection id), and maps `400` field errors onto inputs.
- The test step renders the connection's first-class state (`pending`/`active`/`failed`), shows only the **sanitized** `last_error` category, surfaces an over-privileged warning when present, and offers a retry that re-tests **without** re-entering the password.
- The introspection picker renders discovered tables, columns (name+type), and FKs on **solid** surfaces; lets the owner select `exposed_tables` and approve `exposed_relationships`; and **enforces client-side** that a relationship is approvable only when both endpoints are selected (auto-disabling/deselecting otherwise with a reason) — mirroring `09`'s server-side validation, which remains authoritative.
- The status dashboard shows non-secret config, the live status/`last_tested_at`/sanitized error, the exposure set, and re-test / edit-exposure / edit-config actions — and **never** renders the password.
- Glass appears only on shell chrome; every script, form, table, column, FK, badge, and error/warning sits on a solid surface — a reviewer can confirm no data text renders on glass (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`).
- No request originating from this UI ever carries an `org_id` or `db_connections.id` (anti-IDOR) — asserted in tests.
- The Vitest + RTL suite (step derivation/redirects, consent + re-acceptance, script copy + solid surface, credential validation + write-only password + `400` mapping, test-result + retry-without-password, the relationship both-endpoints guard, save-exposure invalidation, dashboard-hides-password, and no-`org_id` assertions) is green; lint and `type-check` pass with `strict: true`.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| The wizard tracks step in local state and drifts from the server's true connection state, stranding the owner on the wrong step (or re-showing consent for an already-connected org) | Derive the step purely from the connection query (consent/version, row, `status`, exposure); treat the data as the single source of truth; redirect deep links to the unmet gate; cover each state→step mapping with a test |
| A reading-length instruction, the script string, a schema name, or an error message is placed on a `GlassPanel`, hurting legibility of text the owner must read/copy exactly | Constrain glass to the shell's sidebar/topbar/menus; render the script panel, forms, schema lists, badges, and error/warning text on solid surfaces; add a test/review check that no data text lands on glass (`[[../../conventions/glass-only-on-chrome|glass-only-on-chrome]]`) |
| The UI leaks or re-displays the password (pre-fills the field on edit, echoes it back, logs it) | Make the password field strictly write-only and masked — never pre-filled, never returned by the connection query, never shown on the dashboard; on edit, leave it blank/optional and rely on `08` keeping the stored secret; test the dashboard never renders it |
| A raw MySQL/driver error reaches the user via a misrendered `last_error` | Render only the sanitized category `08` returns; never construct error copy from a raw string; the backend already guarantees a closed safe-category set, and the UI trusts only that field |
| The client smuggles or constructs an `org_id`/connection id to scope a request, re-introducing IDOR | The fetch wrapper from `06` never adds a tenant id; mutations send config/selection only; the server scopes by the JWT org (one connection per org); assert in tests that no request body/path carries an `org_id`/connection id |
| The relationship both-endpoints guard is treated as the security boundary, or it diverges from `09`'s server rule | Implement the guard as UX only (disable/auto-deselect with a reason); the server's both-exposed validation in `[[../09-introspection-and-exposure/spec|09]]` stays authoritative; keep the client rule a strict subset that can never approve what the server would reject |
| A large schema (hundreds of tables/columns) causes re-render storms or an unusable picker | Virtualize/paginate the table/column list, expand columns lazily per table, memoize selection state, and avoid re-rendering the whole list on each toggle (`react-best-practices`); test with a large mocked schema |
| `useEffect`+`fetch` patterns cause waterfalls/races across the multi-step flow | Use TanStack Query for the connection query and all step mutations; invalidate on success; disable triggers while pending; `retry: false` on `4xx` (`vercel-react-best-practices`) |
| Empty/too-narrow introspection renders a blank, confusing screen | Provide an explicit empty-state with the likely cause (no visible tables / grant too narrow) and a path back to re-test or fix the credential (scenario 11) |
| Stale `consent_version` silently honored, letting an owner proceed on outdated terms | Drive the consent gate on the *current* version from `07`; force re-acceptance when the version is newer; cover with a test (scenario 10) |
