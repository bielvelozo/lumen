# Query Function Registry — Spec

**Status:** Draft
**Scope:** The registry of predefined, parameterized, read-only query functions — the **only** doors the model has to a customer's data. Define the registry abstraction (each function declares a stable name, a Zod parameter schema, and the exact tables/columns/relationships it needs), the **allow-list guard** that mechanically verifies those needs against the org's `exposed_tables`/`exposed_relationships` ([[../09-introspection-and-exposure/spec|09]]) for the active `db_connections` (org_id from the JWT), and the **backend** safe-SQL builder that turns validated params into a parameterized, read-only MySQL query — plus 1–2 concrete starter functions as worked examples. The model selects a function and supplies validated params; it never writes SQL, identifiers, or fragments. Governed by [[../../rules/data-access-review-gates|data-access-review-gates]].

## Context

This spec is the constitutional heart of the product. Invariant 3 of the [[../../constitution|Constitution]] — *the model never emits free SQL; it only selects among predefined, parameterized, read-only query functions operating only over the tables the owner exposed; the backend executes the SQL* — is not a guideline here, it is the thing this spec **is**. Everything upstream exists to make this boundary real: [[../09-introspection-and-exposure/spec|09]] wrote the least-privilege allow-list (`exposed_tables`, `exposed_relationships`), [[../02-secrets-and-tokens/spec|02]] holds the decryption key outside Postgres, and [[../08-db-connection-create-and-test/spec|08]] proved a live, read-only MySQL handle. This registry is where those converge into the only mechanism by which any business data is ever read.

The differentiator of the product — exact numbers from structured relational data — lives or dies on the integrity of these functions. The database does the math, not the model ([[../../constitution|Constitution]] → *Precision*). So a query function is a small, auditable, parameterized unit: a stable identifier, a Zod schema for its inputs, an explicit declaration of which exposed tables/columns/relationships it touches, and a backend builder that emits a single read-only `SELECT` with placeholders for every value. The model's entire surface to a customer's data is "pick this function, fill these typed params." There is no other door, and "just let the model write this one query" is a constitutional violation, not a shortcut ([[../../rules/data-access-review-gates|data-access-review-gates]]).

The orchestration that exposes these functions to Claude as AI-SDK tools, streams the answer, persists `messages`, and writes `function_call_logs` is **not** here — that is [[../13-chat-orchestrator/spec|13]]. This spec ships the registry, the guard, the builder, and the executor: a pure, testable backend module that, given a function name + raw params + the caller's `org_id`, returns either rows or a typed refusal — with no AI and no HTTP in the loop.

## Problem Statement

After [[../09-introspection-and-exposure/spec|09]], the backend knows exactly which tables, columns, and relationships each org has permitted, but there is no code that can actually *answer a question* over them safely. We need a registry where:

- every readable operation is a **named, predefined function** with a **Zod parameter schema** — the model supplies only validated params (a column choice is a *constrained enum*, never a raw string concatenated into SQL; a date range is two validated dates; a filter is a typed shape, not text);
- each function **declares its data needs** (tables, columns, relationships) in a structured, machine-readable way, so the **allow-list guard** can verify mechanically — before any SQL is built — that every table/column/relationship it would touch is present in the caller's `exposed_tables`/`exposed_relationships` for the org's active connection (org_id from the JWT);
- the **backend** — never the model — builds the SQL: identifiers are resolved only against the exposed allow-list (never string-built from model text), all values go in as bound parameters, the statement is read-only (`SELECT` only), and execution runs against the customer's MySQL with the decrypted read-only credential ([[../02-secrets-and-tokens/spec|02]]) scoped to the active `db_connections`;
- a function that is not parameterized, not read-only, or can reach a table/column/relationship the owner did not expose **cannot be registered or executed** — it is blocked by [[../../rules/data-access-review-gates|data-access-review-gates]].

The worked examples make this concrete: (a) an **aggregate-over-time** function (sum/count/avg of an exposed numeric column, bucketed by a time grain over an exposed date column, within a date range, over one exposed table), and (b) a **filtered count/sum** (an aggregate with simple equality/range filters and an optional group-by, optionally reaching a second table only via an `exposed_relationships` entry — never an arbitrary JOIN).

## Non-Goals

- **The AI-SDK tool-calling wiring, streaming, and logging** — registering these functions as Claude tools, prompting, streaming the answer, persisting `messages`, and writing sanitized `function_call_logs` is [[../13-chat-orchestrator/spec|13]]. This spec's module is consumed by `13`; it does not import the AI SDK.
- **The chat UI** — [[../14-chat-ui/spec|14]].
- **Introspection and exposure** — discovering schema and writing the allow-list is [[../09-introspection-and-exposure/spec|09]]; this spec only *reads* `exposed_tables`/`exposed_relationships`.
- **Connecting / testing the MySQL connection and decrypting the credential** — [[../08-db-connection-create-and-test/spec|08]] and [[../02-secrets-and-tokens/spec|02]]. This spec consumes the read-only handle/credential they provide; it does not own connection lifecycle.
- **A large function catalog.** v1 ships the registry abstraction plus 1–2 starter functions as worked examples. Growing the catalog is later work; each addition must pass the same gate.
- **Column-level exposure semantics beyond the snapshot.** v1 exposes at the table level with a column snapshot ([[../../constitution|Constitution]] → *Scope guardrails*); the guard validates a referenced column against that snapshot but does not introduce per-column allow/deny policy.
- **Free-form / natural-language SQL, an "advanced query" escape hatch, multi-statement queries, CTEs assembled from model input, or any path that concatenates model text into SQL.** These are constitutionally excluded, not deferred.
- **Caching customer data or query results.** No cache in v1 ([[../../constitution|Constitution]]); every call reads live MySQL.

## Constraints

- **The model never emits SQL or identifiers (invariant 3).** A registered function exposes only a Zod-typed parameter object. Any place where the model "chooses" a table, column, relationship, time grain, or aggregate is modeled as a **constrained value** (an enum / id resolved against the allow-list), validated before use. Raw strings from the model are never interpolated into SQL — not as values, and not as identifiers. Governed by [[../../rules/data-access-review-gates|data-access-review-gates]].
- **`org_id` from the JWT, never the client (anti-IDOR).** Execution takes `org_id` from the verified JWT claims passed in by the caller ([[../13-chat-orchestrator/spec|13]]). The active `db_connections`, and the `exposed_tables`/`exposed_relationships` rows it reads, are all resolved by that `org_id`. A connection id or table name supplied in params is only honored after confirming it belongs to the caller's org; otherwise it resolves to nothing and the call is refused. Governed by [[../../rules/data-access-review-gates|data-access-review-gates]].
- **Each function declares its data needs structurally.** A function definition carries a machine-readable manifest of the tables, columns, and relationships it may touch — partly static (fixed tables/columns it always uses) and partly derived from validated params (the column the caller chose, which must itself be one of an allow-listed set). The allow-list guard consumes this manifest mechanically; it never has to parse SQL to know what a function reads.
- **Allow-list guard runs before SQL is built.** For the resolved org + active connection, the guard asserts: every table the function needs ∈ `exposed_tables`; every column it references ∈ that table's `columns` snapshot; every join is backed by an `exposed_relationships` row for that connection (matching `from_*`/`to_*`), never an ad-hoc JOIN. A miss is a **typed refusal** (e.g. table/column/relationship not exposed), not a 500 and not a silent widening.
- **Safe SQL construction by the backend.** The builder emits a single `SELECT` with bound parameters (`?` placeholders via mysql2) for **every** value — date bounds, filter values, limits. Identifiers (table/column names, the chosen aggregate column, group-by column, join columns) are taken **only** from the validated, allow-listed set and quoted/escaped as identifiers by the backend — never concatenated from model-supplied text. Aggregates (`SUM`/`COUNT`/`AVG`) and time grains (`day`/`week`/`month`) come from a closed, backend-defined set keyed by enum, not from model strings.
- **Read-only, single-statement, bounded.** Only `SELECT` is ever produced — no DML/DDL, no multiple statements, no stored-proc calls. The read-only MySQL credential ([[../../constitution|Constitution]] → invariant 5; created in [[../07-db-connection-consent-and-script/spec|07]]) is the backstop, but the builder must independently never emit a write. Apply a sane `LIMIT` / result-size and statement-timeout ceiling so a function cannot return or scan unbounded data.
- **Scoped to the active connection with the decrypted read-only credential.** Execution uses the connection resolved for the org (engine `mysql` in v1), with the password decrypted in the application via [[../02-secrets-and-tokens/spec|02]] — Postgres never sees plaintext. The connection must be `status = 'active'`; a `pending`/`failed` connection yields a typed refusal, not a partial answer.
- **Parameter validation is Zod, and total.** Raw params are parsed by the function's Zod schema before anything else; a parse failure is a typed validation error returned to the orchestrator, never coerced. Schemas are strict (no unknown keys), bound numeric ranges, validate date order (`from <= to`), and constrain enums to the allow-listed sets.
- **Sanitized failures.** Refusals and errors (not exposed, validation failed, connection down, query timeout) carry a sanitized, model-safe message and a stable machine code; they never leak raw schema internals, SQL text, connection secrets, or customer data values — consistent with `function_call_logs.error_message` and `last_error` being sanitized. The actual logging is `13`'s job; this module returns the typed result it will log.
- **Pure and unit-testable.** The registry/guard/builder are decoupled from HTTP and from the AI SDK. Given `(functionName, rawParams, orgId)` plus injectable allow-list and MySQL accessors, the module returns rows or a typed refusal — so the guard and builder can be tested without a live model. SQL string-shape and parameter-binding are assertable in tests.
- **Registering an unsafe function is blocked.** A function that is not parameterized (takes free text destined for SQL), not read-only, or whose declared/derivable needs can reach a table/column/relationship outside the allow-list must fail the gate and not be registerable. This is enforced by [[../../rules/data-access-review-gates|data-access-review-gates]] at review and, where feasible, by the registry's own shape (e.g. a function cannot declare a need it can't express as a structured table/column/relationship reference).

## User Stories / Scenarios

1. **Aggregate over time, happy path.** Orchestrator invokes `aggregate_over_time` with `{ table: "orders", metric: { agg: "sum", column: "total" }, dateColumn: "created_at", grain: "month", from: "2026-01-01", to: "2026-05-31" }`. Zod validates; the guard confirms `orders`, `total`, and `created_at` are exposed for the org's active connection; the builder emits a parameterized `SELECT <bucket(created_at)>, SUM(`total`) ... WHERE created_at BETWEEN ? AND ? GROUP BY ... ORDER BY ...` with bound dates; MySQL returns the monthly sums. Exact numbers, computed by the database.
2. **Filtered sum with an exposed relationship.** Orchestrator invokes `filtered_aggregate` over `order_items` summing `line_total`, filtered by `status = 'paid'`, grouped by a column on `orders` reached **only** via the `orders_items` relationship. The guard verifies both tables are exposed *and* that the join is an `exposed_relationships` row; the builder constructs the JOIN solely from that row's `from_*`/`to_*`, all filter values bound. No arbitrary JOIN is possible.
3. **Column not exposed → typed refusal.** The model picks a column that is not in the table's snapshot (or a table not exposed at all). The guard rejects before any SQL is built, returning a sanitized "field not available" refusal the orchestrator can relay — no query runs, nothing leaks.
4. **Bad params → validation error.** Params arrive with `from > to`, an out-of-range limit, or an unknown aggregate. Zod fails fast; a typed validation error is returned. No guard, no SQL, no DB call.
5. **Cross-tenant attempt fails.** Params reference a `db_connection_id` or table belonging to another org. Because the active connection and allow-list are resolved by JWT `org_id`, the reference resolves to nothing and the call is refused — no introspection, no read, no leak.
6. **Connection not active.** The org's connection is `pending`/`failed` (or unreachable at call time). The executor returns a sanitized "data source unavailable" refusal rather than a stack trace or partial result.
7. **Attempted free-SQL / injection.** The model emits a string like `total; DROP TABLE orders` where a column is expected. Because the column param is an enum constrained to the exposed snapshot, validation rejects it; nothing is interpolated. (Asserted by test.)
8. **Adding a new function safely.** A developer registers a third function. It declares its tables/columns/relationships structurally, ships a Zod schema and a builder that only parameterizes values and only uses allow-listed identifiers, and passes the data-access gate. A reviewer can confirm read-only + parameterized + allow-list-bounded by reading the declaration, not the SQL.

## Success Criteria

- A registry abstraction exists where each function has a **stable name**, a **Zod parameter schema**, a **structured declaration** of the tables/columns/relationships it may touch (static + param-derived), an **allow-list guard**, and a **backend SQL builder + executor**. Functions are looked up by name; an unknown name is a typed error.
- The guard mechanically verifies, against `exposed_tables`/`exposed_relationships` for the org's active connection (org_id from JWT), that every table, column, and relationship a function would touch is exposed — **before** SQL is constructed. A miss returns a typed refusal and runs no query.
- The builder emits a **single read-only `SELECT`** with **bound parameters for every value** and identifiers drawn **only** from the validated allow-listed set; aggregates and time grains come from closed backend enums. Verified by tests asserting the SQL shape, the placeholder/parameter binding, and that no model-supplied string is ever concatenated into SQL.
- Execution runs against the customer's **MySQL** using the **decrypted read-only credential** for the **active** connection, with a `LIMIT`/result ceiling and statement timeout. Postgres never sees the plaintext secret.
- Two starter functions are implemented and tested end-to-end against a seeded MySQL fixture: `aggregate_over_time` (sum/count/avg by time bucket over a date range on one exposed table) and `filtered_aggregate` (count/sum with equality/range filters + optional group-by, joining a second table only via an `exposed_relationships` entry). Both return exact, DB-computed numbers.
- Anti-IDOR holds: a second org cannot execute a function against another org's connection/tables; cross-tenant references resolve to nothing. Covered by test.
- Injection is impossible by construction: a column/table/relationship param carrying SQL is rejected at validation/guard time; a test asserts no such string reaches the SQL builder.
- Every failure mode (not exposed, validation failed, connection inactive/unreachable, timeout) returns a **sanitized, typed** result with a stable code and no leak of schema, SQL, secrets, or customer values.
- The module is pure with respect to HTTP and the AI SDK: `(functionName, rawParams, orgId)` + injected accessors → rows or typed refusal. Tests run without a live model.
- A reviewer can confirm, per the [[../../rules/data-access-review-gates|data-access-review-gates]] checklist, that no function is non-parameterized, non-read-only, or able to reach an unexposed table/column/relationship.

## Risks and Mitigations

| Risk | Mitigation |
|---|---|
| Model-supplied text reaches SQL as an identifier (table/column), opening injection / unexposed access | Model never supplies identifiers as raw strings; column/table/relationship choices are enums resolved against the allow-list snapshot; the builder takes identifiers only from the validated set and escapes them as identifiers; test asserts no model string is concatenated into SQL |
| A function quietly reaches a table/column/relationship the owner did not expose, widening the allow-list | Functions declare their needs structurally; the guard checks every need against `exposed_tables`/`exposed_relationships` for the active connection **before** building SQL; a miss is a typed refusal, not a partial run; covered by tests |
| A join sneaks in that is not backed by an `exposed_relationships` row (arbitrary JOIN) | Joins may be built **only** from an `exposed_relationships` row's `from_*`/`to_*`; the builder cannot emit a JOIN without one; test asserts an unbacked join is refused |
| `org_id` taken from a client/model-supplied connection id or table name instead of the JWT (IDOR) | Resolve the active connection and allow-list by JWT `org_id`; treat any supplied id/name as a filter confirmed against that scope, never as the source of truth — per [[../../rules/data-access-review-gates|data-access-review-gates]] |
| A function emits a write, multi-statement, or stored-proc call, breaking read-only | Builder produces a single `SELECT` only; read-only MySQL credential ([[../07-db-connection-consent-and-script/spec|07]]) is the backstop; tests assert statement shape and that no DML/DDL is ever generated |
| An aggregate/filter scans or returns unbounded data, degrading the customer DB | Apply a backend `LIMIT`/result ceiling and a statement timeout on every function; reject params that would defeat the bound; document the ceiling |
| The decrypted read-only secret or raw SQL/schema leaks via an error message | All refusals/errors are sanitized with stable machine codes; never include SQL text, secrets, schema internals, or customer values; mirror the sanitization of `function_call_logs.error_message` |
| A new function is added that is non-parameterized / non-read-only / over-reaching, bypassing the contract | [[../../rules/data-access-review-gates|data-access-review-gates]] blocks it at review; the registry shape forces structured need-declaration so over-reach is visible, not hidden in SQL |
| Column snapshot in `exposed_tables` drifts from the live MySQL (dropped/renamed column), so a guarded query fails at execution | Guard against the snapshot but treat the live query failure as a sanitized refusal; document that the snapshot is point-in-time ([[../09-introspection-and-exposure/spec|09]]); re-exposure refreshes it; the allow-list still bounds what can be attempted |

## Open Questions

- [NEEDS CLARIFICATION: the exact shape of a function's structured "needs" declaration — a static manifest of fixed tables/columns plus a typed mapping from param fields to allow-listed columns, vs. a fully data-driven descriptor the builder interprets generically. Default lean: a typed declaration object per function that the guard reads field-by-field, so adding a function is "declare needs + Zod schema + builder," not "write a guard."]
- [NEEDS CLARIFICATION: filter expressiveness for `filtered_aggregate` in v1 — equality and range only, or also `IN`, `IS NULL`, and simple `OR` groups? Default lean: equality + range (`>=`/`<=`/`BETWEEN`) on exposed columns in v1; richer predicates are later, each still bound and allow-listed.]
- [NEEDS CLARIFICATION: time-grain set and bucketing strategy across MySQL versions — fixed `day`/`week`/`month`/`quarter`/`year` via `DATE_FORMAT`/`YEAR()`+`MONTH()` etc., and how the week/quarter boundary and timezone are defined. Default lean: `day`/`week`/`month` in v1, UTC buckets, documented; timezone handling deferred.]
- [NEEDS CLARIFICATION: how a numeric/date column's *type* (from the snapshot) is validated as appropriate for an aggregate or a date bucket — does the guard enforce "metric column must be numeric, date column must be a date/datetime type," and how strictly given MySQL type strings? Default lean: enforce a coarse type-family check from the snapshot and refuse mismatches.]
- [NEEDS CLARIFICATION: result-size/row-count and statement-timeout ceilings — concrete defaults (e.g. max grouped rows returned, max scan time) and whether they are global or per-function. Resolve alongside [[../13-chat-orchestrator/spec|13]] so the orchestrator can surface "result too large / timed out" cleanly.]
- [NEEDS CLARIFICATION: how identifiers from the allow-list are safely quoted for MySQL (backtick-escaping vs. an allow-list-only-charset assertion derived from introspection), to guarantee even allow-listed names can't break out of identifier position.]
